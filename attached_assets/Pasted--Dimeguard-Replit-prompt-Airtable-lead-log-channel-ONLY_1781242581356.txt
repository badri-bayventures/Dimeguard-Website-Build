## Paste to the Dimeguard Repl agent

PROJECT: Dimeguard website (Next.js, App Router). The lead pipeline (`src/app/api/lead/route.ts` + `src/lib/leads.ts`) currently sends one notification email via Resend. Add ONE new channel — an Airtable record — that fires alongside the email. Do NOT add SMS/Twilio (explicitly deferred). Do NOT modify the email behavior, the contact form's UX, the route's validation/responses, calculators, brand tokens, or Notion.

INSPECT FIRST
- Read `src/lib/leads.ts`: the `Lead` type is `{ name, email?, phone?, message?, source, receivedAt }`, and `notifyLead()` currently awaits `sendLeadEmail()` and throws on failure (the route turns that into a 502).

IMPLEMENT — `createLeadRecord(lead: Lead)` in `src/lib/leads.ts`, using the Airtable REST API directly (no SDK):
- Enabled only if `AIRTABLE_API_KEY`, `AIRTABLE_BASE_ID`, and `AIRTABLE_TABLE_NAME` are ALL set; otherwise return a skipped status without logging an error (clean no-op — this is by design).
- POST `https://api.airtable.com/v0/${AIRTABLE_BASE_ID}/${encodeURIComponent(AIRTABLE_TABLE_NAME)}` with `Authorization: Bearer ${AIRTABLE_API_KEY}` and body:
  ```json
  {
    "records": [{ "fields": {
      "Name": lead.name,
      "Phone": lead.phone,        // omit key if undefined
      "Email": lead.email,        // omit key if undefined
      "Comment": lead.message,    // omit key if undefined
      "Source": lead.source,
      "Status": "New"
    }}],
    "typecast": true
  }
  ```
- `"typecast": true` is REQUIRED — it lets new `Source` values auto-create select options.
- Do NOT write `Submitted At` (it's an Airtable created-time field), `Page`, or `Resource ID` (reserved for future calculator/resource lead gates).
- Throw on non-2xx with the Airtable error message included.

WIRE INTO `notifyLead()` — email remains the success criterion, Airtable is best-effort:
- Run both channels concurrently (e.g. `Promise.allSettled([sendLeadEmail(lead), createLeadRecord(lead)])`).
- If the EMAIL channel rejected, rethrow its error — the route's current 502 behavior and the visitor-facing success/error states must not change in any way.
- If the Airtable channel rejected, log it server-side (`console.error("[lead] airtable channel failed", …)` — message only, no PII dump) and continue. An Airtable outage must never fail the submission.

OFF-LIMITS
- The Resend email path (logic, env names, from/to, replyTo), the contact form markup/UX, the route's validation rules and response shapes, the honeypot, calculators, Notion/blog, all other pages.
- No new client-exposed `NEXT_PUBLIC_` vars. Server-side only.
- No `twilio` package, no SMS code — deferred deliberately.

ENV (set in Replit Secrets; Badri mirrors to Vercel for production):
- `AIRTABLE_API_KEY` — personal access token
- `AIRTABLE_BASE_ID` = `appYuTgqVVZLVAx98`
- `AIRTABLE_TABLE_NAME` = `Leads`

WHEN DONE
- List files changed (should be `src/lib/leads.ts` only, plus possibly a comment touch-up in the route).
- Confirm: a contact-form submission on the preview (a) still emails exactly as before, (b) creates an Airtable row with Source "Website contact form" and Status "New", and (c) with the three env vars removed, the channel cleanly no-ops and submissions still succeed.
